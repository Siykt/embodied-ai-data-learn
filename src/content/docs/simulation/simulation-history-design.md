筹备一场演出，最初可能只需要舞台和演员。等到要反复排练、比较不同方案、让其他人复演，就还需要统一的剧本、机位、场记和评价标准。只留下一段录像，后来的人很难知道当时怎样安排，哪里出了问题。

具身仿真也经历了类似的发展：先让虚拟机器人在场景中运行，再逐步补上任务规则、传感器、记录器和评测方法。这些层共同决定一份数据能否复现和使用。**类比只帮助理解分工**：机器人运动由数学模型计算，能否代表真实设备还需要测量验证。

读完本页，你应能把一项新能力对应到它要解决的问题：为什么需要物理计算、统一任务、过程记录与真实验证，而不必先记软件年表。

## Why｜为什么仿真会发展出这么多层

因为要回答的问题在增加。让机械臂“动起来”，与证明它“能抓稳杯子”，需要留下的证据不同；让别人用这次抓取训练模型，又要再保存动作、观测和时间关系。

以“把杯子放到托盘”为例，最初只想看到机械臂动起来；随后想知道它能否拿稳、换个杯子还能否完成，以及能否把练习记录交给别人使用。每增加一个问题，都需要补上相应的模型、规则或数据。

![接触、视觉、比较、规模和真实部署需求分别推动物理配置、观测、任务、记录和验证设计](/images/docs/simulation-history-design-drivers.svg)

例如，比较两种抓法时，要给它们相同的杯子和成功规则；研究真实夹爪时，则需要测量摩擦与延迟。前者推动标准任务，后者推动校准和真实对照。

理解发展史时可以始终追问：**这一项设计解决了什么数据问题，又增加了什么记录责任？** 软件发布日期只是定位这些变化的线索。

## What｜是什么：一套能够复现实验的数据系统

一次仿真可以这样理解：准备机器人和场景，发出动作，计算运动，得到观测，再把过程与结果保存下来。下面五层把这条过程分开管理。

![具身仿真的五层结构：场景与资产、物理与传感器、任务环境、数据记录器、评测与真实对照](/images/docs/simulation-history-stack.svg)

沿着放杯子的任务看：先给出杯子和机器人的形状、重量与位置；再计算动作后杯子如何运动，以及相机能看见什么。任务程序判断是否放好，记录器保存每一步，评价程序检查结果。

这五层依次回答：**世界是什么、动作后会怎样、怎样算完成、发生过什么、结果是否可信。** 初学时先记住这些问题，就能理解为什么单独一段动画不足以说明一次实验。

### 一次尝试与一份数据集有什么区别

从初始状态到结束的一次完整尝试叫 **episode**。策略实际执行时形成的过程记录常叫 **rollout**。例如，抓杯子失败后重置场景并重试，应得到两个 episode，不能把前后状态当成连续运动。

许多任务提供 `reset` 和 `step` 两个入口：前者把任务放回初始状态，后者接收动作并推进一次。接口相似，只说明调用方式接近；同样叫“结束”，可能代表成功、失败，也可能只是时间用完。数据集中仍须写明具体含义。

## Who｜谁负责让这些层协同工作

**引擎负责计算，任务程序负责组织，使用者负责选择并核对实验条件。** 在一个人的学习项目里，也能把这三件事分开检查。

例如，杯子下落的速度异常，先查模型与物理计算；杯子没放稳却显示成功，先查任务规则；视频和动作对不上，则查记录时间。分层让我们知道问题大概出在哪里。

常见工具可以先这样认识：MuJoCo 提供运动与接触计算；Isaac Sim 组合场景、画面和传感器；Isaac Lab 组织任务与批量练习。Gazebo 常用于机器人软件与传感器系统联调。它们都有具体版本和能力范围，下一章会继续解释如何选择。

人还需要确定“放好了”的含义。例如，杯子在托盘上松手并稳定两秒可以作为一个示例规则；只碰到托盘就停止，是另一种规则。规则不同，数据中的成功标记也会不同。

## Where｜数据在哪里产生，又流向哪里

**数据从准备场景时就开始产生，最后供训练、复盘和独立测试使用。** 杯子尺寸、动作设置与任务规则都会改变后面记录的含义。

![抓杯子任务从定义目标、准备模型、采样观测、生成变化、保存记录到真实验证的路径](/images/docs/simulation-history-grasp-example.svg)

继续把“拿起”扩展到“放进托盘”，可以沿四个时刻看数据：

1. **开始之前：**写下杯子摆在哪里、机器人用哪个模型，以及怎样才算放好。这是实验条件。
2. **执行过程中：**保存相机看到的画面、夹爪收到的命令和执行后的状态，并记住它们各自的时间。这是过程记录。
3. **结束之后：**分别标明放好、滑落或超时。失败也提供信息，不能只留下成功视频。
4. **再次使用时：**说明记录来自哪次尝试。训练可以利用这些样本，评测还需要留出没拿来训练的新条件。

采集者与使用者还要约定每列数据的含义、单位和时间关系。这份约定称为**数据契约**，字段的结构称为 **schema（数据模式）**。具体怎样实现，会在后面的[技术链路](/simulation/simulation-scene-physics/)逐章展开。

### 扩大规模前，要先决定哪些部分必须准确

若目标是研究滑落，接触和摩擦就需要重点验证；若目标是训练视觉策略，相机、遮挡和图像分布也必须检查。图像逼真程度与动力学准确程度要分别评价。

复杂模型会增加计算与保存成本，极简模型又可能漏掉关键失败。可以先用少量数据确认任务敏感的因素，再测量包含渲染与写盘的有效 episode 产量。并行环境越多，越需要防止把不同环境、不同重置之间的记录接错。

## When｜何时出现这些变化：代表性发展时间线

先了解上面的需求，再看时间线，就能看出每个节点补上了什么能力。**下列年份是代表性论文或项目节点**，不表示某项能力首次出现，也不表示此前的工具已被淘汰。

![从机器人系统集成、接触控制、标准任务，到真实迁移、离线数据和并行多传感器工作流的发展节点](/images/docs/simulation-history-timeline.svg)

| 代表时期与资料 | 当时突出的需求 | 设计变化及数据影响 |
| --- | --- | --- |
| 2000 年代：2004 年 [Gazebo 论文](https://doi.org/10.1109/IROS.2004.1389727) | 先在虚拟世界联调机器人、传感器和任务对象 | 组织场景、物理、传感器与机器人软件，记录接近机器人系统接口的试验过程 |
| 2012 年：[MuJoCo 论文](https://doi.org/10.1109/IROS.2012.6386109) | 抓取、行走等接触任务需要高效且可配置的动力学 | 专注模型、执行器、接触与求解，便于研究高频状态、动作和接触轨迹 |
| 2016—2018 年：[OpenAI Gym](https://arxiv.org/abs/1606.01540)、[DeepMind Control Suite](https://arxiv.org/abs/1801.00690) | 不同方法需要统一任务入口和可比较成绩 | 统一重置、动作与观测等接口；比较数据时仍须核对成功、终止与超时语义 |
| 2017 年后：[视觉领域随机化](https://arxiv.org/abs/1703.06907)、[动力学随机化](https://arxiv.org/abs/1710.06537) | 仿真外观与动作响应和真实设备不同 | 在受控范围内改变场景或动力学参数，扩大覆盖；须记录范围与每次实际取值 |
| 2020 年：[D4RL](https://arxiv.org/abs/2004.07219) 等离线基准 | 重复利用已有轨迹，无需每次在线采样 | 数据集和离线评测协议更加突出，来源、结束语义、质量与划分成为关键 |
| 2021 年：[Isaac Gym](https://arxiv.org/abs/2108.10470) | 机器人学习需要大量交互 | GPU 并行物理与训练流水线提高轨迹产量，渲染和写盘仍可能限制有效产量 |
| 2020 年代：[Isaac Sim](https://docs.isaacsim.omniverse.nvidia.com/latest/index.html)、[Isaac Lab](https://isaac-sim.github.io/IsaacLab/main/index.html) 工作流 | 组合复杂资产、视觉传感器、并行任务与示教 | 集成场景、传感器和任务配置，让图像、深度、分割、动作与标签进入共同的数据流程 |

这些路线至今仍会同时使用。Gazebo 的系统联调、MuJoCo 的接触控制实验，以及 Isaac Sim/Lab 的资产与多传感器工作流，可以服务同一个项目中的不同环节。D4RL 是离线数据发展的代表性节点，也不意味着所有具身数据都应采用它的格式。

### 从扩充仿真变化，到用真实数据校准

表中的**领域随机化**是有计划地改变外观、物体位置或物理参数，让训练数据覆盖更多情况。**系统辨识**则用真实设备的测量，估计摩擦、延迟等模型参数。前者扩大覆盖，后者缩小关键参数的不确定范围；都需要真实对照，不能用“随机得更广”替代验证。

校准用过的真实样本，不能同时承担独立测试的角色。应保留未用于调参的任务和样本，检查仿真数据带来的提升能否延续到真实设备。这也是从仿真到真实迁移（sim-to-real）需要报告的证据。

### 入门时，什么时候进入下一步

不必按发布日期学习软件。按数据能否解释来推进更直接：先看懂一个模型的单位和关节，再跑通固定动作，然后添加一个带时间的传感器；能解释一条轨迹后，才增加成功条件、场景变化与真实对照。

一个合适的起点是[旋转关节实验](/simulation/mujoco-data-walkthrough/)：它只有一个关节，却能让你核对“命令、运动、传感器、记录时刻”之间的关系。把这条关系弄清，再扩展到机械臂和并行数据生成。

### MuJoCo、Isaac Sim 与 Isaac Lab 分别承担什么

**MuJoCo**提供物理引擎及模型接口，常被用于关节控制、接触和状态轨迹实验；任务定义和导出规则仍要由项目或上层任务库补齐。它也能生成图像和数值传感器数据。模型通常用 **MJCF** 描述，这是保存机器人、场景、传感器和执行器配置的格式；**MJX** 则提供基于 JAX 的批量仿真路径，使用前要核对支持的模型特性与数值差异。

**Isaac Sim**组织更广的场景、资产、渲染和传感器工作流；**Isaac Lab**建立在它之上，组织机器人学习任务与并行运行。其场景常用 **USD** 组织，即能保存并引用场景对象与资产的格式体系。复现数据时，要一起保存 Lab/Sim 版本、场景依赖和任务配置。

**Gazebo**常用于与机器人软件、ROS 传感器链路联调。这些工具服务的工作环节有重叠，也各有使用场景。选择入口可看[仿真器与具身数据](/simulation/simulators-embodied-data/)，具体路线见 [MuJoCo](/simulation/mujoco-embodied-data/) 与 [Isaac Lab](/simulation/isaac-lab-embodied-data/)。

</details>
