description: 以机械臂把杯子放进托盘为例，理解引擎、平台与任务框架的分工，并根据要采集的数据选择实践起点。
---

选拍摄设备时，通常先想清楚要拍什么：孩子跑步、室内证件照，还是远处的飞鸟。拍摄对象不同，对速度、镜头和光线的要求就不同；选择仿真器也可以从“我要记录什么”开始。

本页一直用一个任务举例：**让机械臂把桌上的杯子放进托盘，并把过程保存成可用的数据。** 仿真器依据模型生成运动和画面，生成得是否合理，还需要与真实测量对照。

读完这页，你应能分清**物理引擎、仿真平台和任务框架分别负责什么**，并为自己的数据需求选出一个实践起点。工具的详细对比放在页末，需要选型时再展开查阅。

## Why｜为什么要从数据目标选择仿真器

**因为同一个放杯子任务，要回答的问题不同，需要保存的数据就不同。**

如果想知道机械臂为什么没夹稳，要看动作、关节运动和接触记录。如果想训练机器人“看着杯子去抓”，就需要连续画面，以及每幅画面对应的动作。如果想判断换一种杯子后还能否成功，则要保存多次尝试的条件和结果。

这就像拍运动视频：只有一张清晰照片，仍然无法判断运动员如何完成整套动作。仿真数据也是如此——画面、动作和结果都要围绕用途来记录。先确定要交付什么，才能判断工具是否合适。

## What｜是什么：从虚拟实验到可使用数据的工具链

**仿真器根据场景和动作，计算下一刻会发生什么；采集流程把这些结果变成可回读的数据。**

对放杯子任务来说，你先准备桌子、杯子、托盘和机械臂，再发出移动或夹爪闭合的命令。仿真器计算杯子是否被夹住、怎样移动，并按配置生成相机画面和关节读数。

### 端到端技术链路

把整条流程先记成三件事：**准备实验 → 执行并记录 → 回读检查**。下图展开了每件事内部的工作，第一次阅读时先沿着箭头看顺序即可。

![仿真数据依次经过任务定义、场景、物理、传感器、任务运行、批量生成、记录与评估](/images/docs/simulation-end-to-end-chain.svg)

准备实验时，要说明杯子从哪里开始、怎样才算放好。执行时，要同时记录机器人看到了什么、做了什么、杯子怎样变化。回读时，要能从一次动作找到前后画面与状态，确认记录没有接错。

一次从重置到结束的完整尝试称为 **episode**，其中实际执行的过程记录常称为 **rollout**。杯子掉了以后重新来一次，就产生一个新的 episode，应有新的编号。

## Who｜谁负责物理、任务和数据记录

**引擎计算运动，平台组织场景与传感器，任务框架规定玩法，记录器保存过程。**

这些名称描述的是分工。一套软件可以覆盖多个环节，但选型时仍要逐项确认：本次放杯子任务由谁完成这些工作。

| 分工 | 在放杯子任务里负责什么 | 常见入口 |
| --- | --- | --- |
| 物理引擎 | 算机械臂怎么动、杯子是否滑落 | MuJoCo 等 |
| 仿真平台 | 组织机器人、场景、相机与渲染 | Isaac Sim 等 |
| 任务框架 | 定义动作、观测、重置和成功条件 | Isaac Lab、robosuite 等 |
| 记录器 | 把画面、动作、状态与结果写成文件 | 项目采集程序或框架中的导出流程 |

先按眼前最需要看懂的数据选择起点：

- **先看懂动作怎样改变关节运动：**从 [MuJoCo 与具身数据](/simulation/mujoco-embodied-data/)开始，再读取一条实际轨迹。MuJoCo 也能生成图像；这里选择它，是为了先缩小实验范围。
- **需要组织场景、多种传感器与并行机器人任务：**从 [Isaac Lab 与具身数据](/simulation/isaac-lab-embodied-data/)开始，分清 Isaac Sim 的场景与传感器工作流，以及 Isaac Lab 的任务配置。
- **已有机器人项目或任务库：**先沿用现有入口跑通一次采集。比如 ROS 项目可调查 Gazebo，已有 MuJoCo 操作任务可调查 robosuite，再检查输出能否满足需求。

“选起点”只需确定先验证哪条路线。真正决定采用哪套工具，要等同一个最小任务能运行、导出和回读之后。

## Where｜数据保存在哪里，哪些说明必须一起交付

**数据要保存成能独立读取的文件，并带上解释动作、时间和实验条件的说明。**

例如，看到视频里的杯子落进托盘后，使用者应能找到：这是哪次尝试、当时发了什么动作、下一刻杯子在哪里，以及为什么判定成功。仅有查看器里的动画，无法回答这些问题。

### 通用数据契约

**数据契约**就是采集者和使用者对“每个字段是什么、怎样对应”的约定；字段结构也称为 **schema（数据模式）**。可以把它看成数据随附的使用说明。

![一个 episode 包含元数据、带时间的观测、动作与状态、真值来源，以及边界和质量信息](/images/docs/simulator-data-contract.svg)

先记住一条最小连接：**当前画面和状态 → 本次动作及其生效区间 → 下一画面和状态**。最终状态可能没有后续动作，不能为了凑齐行数而补一个动作。[旋转关节实验](/simulation/mujoco-data-walkthrough/)提供了可下载核对的实例。

<details>
<summary>采集时速查：字段、来源与结束标记</summary>

| 一起保存的内容 | 至少回答什么问题 |
| --- | --- |
| 元数据 | 哪个任务、机器人、场景、引擎和生成脚本版本？用了什么随机种子？ |
| 观测 | 图像、关节状态、IMU、接触来自哪里？单位、坐标系、标定与时间是什么？ |
| 动作与状态 | 命令是位置、速度、力矩还是末端目标？何时生效？连接哪两个状态？ |
| 标签与来源 | 物体位置、分割和接触来自引擎真值，还是由观测估计？ |
| 边界与质量 | 哪次尝试的开始和结束？为何结束？是否成功？是否通过质检？ |

如果有奖励和结束标记，也要解释它们的含义。`terminated` 通常表示任务按定义自然结束，`truncated` 表示因时间限制等条件截断；具体规则仍以任务版本为准。不能只保存一个未解释的 `done`。

</details>

### 真值应该交给谁使用

仿真器知道杯子的精确位置，这类引擎内部状态称为**仿真真值**。它可以帮助制作标签、定位问题和检查结果。

但如果真实机械臂只能通过相机找杯子，训练时就要分清“让机器人看的画面”和“供评估使用的精确位置”。直接把精确位置交给它，测到的成绩无法说明它是否学会了从图像找杯子。保存数据时，要标明哪些是策略观测、哪些是辅助标签、哪些是评估真值。

## When｜什么时候选工具，什么时候扩大采集

**先跑通一小批完整数据，确认能用，再扩大采集。**

1. **开始前，写清用途。** 本次是训练机器人看图抓杯子，还是检查夹爪运动？把必需的画面、动作、结果和目标真实设备写下来。
2. **选型时，让候选工具做同一次放杯子任务。** 对齐初态、动作含义和成功条件，确认每条记录都能回读，并能说明成功或失败的原因。
3. **扩大前，检查变化是否有效。** 再加入不同杯子、位置或光照，确认新场景仍能完成任务，记录也没有错位。物理运行得快，不等于每秒能交付的有效数据多；还要把渲染、质检和写盘算进去。
4. **评测前，保留独立样本。** 保存环境与任务版本，让未参与调参的场景、物体和真实数据检验结果。

### 质量检查清单

先做一次具体检查：任取放杯子过程中的一帧，找到它对应的状态、接下来的动作和下一状态。能接起来，再用下面的清单检查其他问题。

<details>
<summary>采集前后速查：时间、传感器、接触与评估</summary>

| 采集阶段 | 最先检查的内容 |
| --- | --- |
| 第一条轨迹完成后 | 动作对应的前后状态是否正确，时间是否重复或倒退 |
| 加入相机或 IMU 后 | 坐标、分辨率、内参、深度单位、轴方向与采样时刻是否齐全 |
| 加入接触任务后 | 穿透、抖动、限位、摩擦和执行器响应是否合理 |
| 增加场景变化后 | 新任务是否可达，有没有把无效初态当成普通失败 |
| 划分训练与评估时 | 同一原始轨迹或近重复场景是否泄漏到两边 |
| 报告结果时 | 是否说明环境版本、任务规则、尝试数及真实对照条件 |

</details>

图像看起来逼真，不代表动作响应准确；引擎真值很干净，也不代表真实传感器能给出相同信息。选型结论应写成可以复查的结果，例如“这套配置能保存所需画面与动作，且通过时间对齐检查”。

## 工具选型参考

需要确定模型格式、导出责任或其他候选工具时，再展开下面的对照。表格说明调查方向，不用于速度或精度排名。

<details>
<summary>MuJoCo 与 Isaac 路线：模型、任务、导出和复现</summary>

### MuJoCo 与 Isaac Lab：按数据任务比较

| 数据问题 | MuJoCo 路线 | Isaac 路线 |
| --- | --- | --- |
| 场景怎样定义 | MJCF 描述模型、场景、传感器和执行器，引用网格与纹理 | Isaac Sim 用 USD 组织场景与资产，Isaac Lab 添加任务配置 |
| 谁运行任务 | 项目环境，或 dm_control、robosuite 等上层任务库 | Isaac Lab 的环境与任务配置 |
| 可以记录什么 | 状态、动作、接触、数值传感器及按配置生成的图像 | 并行任务状态、动作、图像、多传感器观测及任务标签 |
| 谁规定导出格式 | 项目记录器或所用任务库的导出流程 | 所用工作流及项目记录器、导出流程 |
| 复现需要保存什么 | 模型与资产版本、求解配置、步长、种子、任务代码 | Lab/Sim 版本、USD 依赖、任务代码及每次采样的参数 |

**MJCF** 是 MuJoCo 的模型描述格式；**USD** 是 Isaac Sim 用来组织场景和引用资产的格式体系。它们保存实验条件，不能替代时间、动作和结果记录。**MJX** 提供基于 JAX 的 MuJoCo 批量仿真路径，使用前应检查所需模型特性、传感器和数值行为的支持情况。

MuJoCo 可作为研究关节控制、接触和状态轨迹的起点，也能做视觉任务。Isaac Sim 提供场景、渲染与传感器工作流，Isaac Lab 在其上组织机器人学习与并行任务；Mimic 等示教扩增流程还需要相应任务配置和示教输入。是否满足项目要求，要用目标场景、硬件和导出流程验证。详细步骤见 [MuJoCo 与具身数据](/simulation/mujoco-embodied-data/) 和 [Isaac Lab 与具身数据](/simulation/isaac-lab-embodied-data/)。

MJX、Isaac Lab、Genesis 等并行路径应在目标硬件上测完整流程，包括传感器、渲染、质检和写盘。物理每秒步数不等于每秒可交付的有效数据量。

</details>

<details>
<summary>其他候选工具，以及 Genesis、PyBullet 和 Habitat 的能力边界</summary>

### 其他工具分别从哪里开始评估

下表给出调查入口。它说明常见的工作方向，不能直接用于速度或精度排名。

| 工具 | 可从什么数据需求开始调查 | 使用前优先核对什么 |
| --- | --- | --- |
| Genesis | 并行物理实验、程序化场景与轨迹生成 | 当前版本的求解器、模型和传感器支持，硬件与导出接口 |
| PyBullet / Bullet | 使用 Python 与机器人模型快速验证轨迹和采集流程 | 所需接触、控制与相机行为能否通过任务级验证 |
| Gazebo | 将相机、激光、IMU 等仿真记录接入 ROS 工具链 | 物理后端、传感器插件、消息与时间语义 |
| SAPIEN / ManiSkill | 柜门、抽屉等部件交互，以及操作任务基准 | 资产关节定义、任务版本、示教来源和评测规则 |
| Habitat | 室内视觉导航、交互和多智能体任务 | 所选版本、场景资产、物理功能与任务定义 |

**Genesis 的能力需要按发布范围核对。** 项目对生成式仿真和自动数据生成的描述，不应直接解释为“安装基础包后，就能用自然语言生成场景、对象和机器人”。若任务依赖这项能力，应在当前官方文档中找到可运行的具体接口、模型依赖和示例，再验证生成结果的物理有效性与数据来源。仅凭演示视频，无法确认它已是基础物理包的可用功能。

**PyBullet 的数据能否用于研究，要由任务验证决定。** 不能因为它常用于教学或原型，就一概断定物理或渲染结果不可用。同样，Habitat 的导航生态也不能用来推断它的所有版本都只支持简化物理。比较时应注明后端、求解设置、场景和采样方式。

还可按现有生态选择入口：**robosuite** 提供基于 MuJoCo 的操作任务，可结合 [robomimic](https://robomimic.github.io) 组织模仿学习数据；**CoppeliaSim** 提供通用机器人仿真与脚本接口，使用时核对具体许可；**AI2-THOR / ThreeDWorld** 可用于室内视觉和物理交互任务研究。

</details>
