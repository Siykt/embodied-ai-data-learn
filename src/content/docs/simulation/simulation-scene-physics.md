为机器人搭建练习场，和为搬运练习布置一间房间很像：先决定要搬什么，再摆好桌子、箱子和通道。如果练习是搬重箱，纸板做的空箱虽然外观逼真，也不能教会人怎样用力。

仿真里同样如此。接下来一直用“机械臂把杯子放到托盘上”这个任务来说明：桌子、杯子和托盘组成场景，机器人模型描述手臂与夹爪，物理配置决定杯子有多重、会不会滑落。它们共同决定最后记录的动作和轨迹是否有用。

读完本页，你能判断一个虚拟练习场是否准备好了：杯子尺寸对不对、机械臂动作是否合理，以及开始采数据前还要检查什么。外观逼真只是起点，重量与摩擦仍需要测量或明确的假设来支持。

<span id="1-从数据目标反推场景规格"></span>

## Why｜为什么生成数据前要先检查场景？

场景决定了机器人究竟在练习什么；场景有偏差，采得越多，重复的偏差也越多。假设夹爪在仿真中轻轻一夹就能提起杯子，真机却总是滑落，原因可能只是仿真杯子太轻、表面摩擦太大。

对于放杯子任务，可以先问：这批数据要教机器人认出杯子，还是教它稳稳地拿起并放下？前者更关心图像里的外观和遮挡，后者还要关心重量、摩擦和接触。数据用途决定哪些细节需要认真建模。

![任务需求依次确定场景资产、机器人模型、物理配置和可复现的场景版本](/images/docs/simulation-assets-chain.svg)

开始时用几句话写清练习场：哪台机械臂从哪里拿杯子，放到哪个托盘，杯子和托盘能摆在哪些位置。然后量好尺寸、确定位置的参考原点。需要保存的版本和字段放在本页附录中，便于实际配置时逐项核对。

## What｜是什么共同决定了机器人在场景里的行为？

物体的形状、机械臂的身体与驱动方式，以及接触时的物理反应，共同决定杯子能不能被拿起、移动和放稳。下面沿着这三个动作看模型里有什么。

<span id="2-资产与格式视觉几何不等于碰撞几何"></span>

### 物体既有外观，也有参与碰撞的形状

杯子的把手在图像里清楚可见，不代表夹爪真的能伸进去。模型可能用一个简单圆柱计算碰撞，把把手附近的空隙也挡住了。

用于画出外观的形状叫**视觉几何**；用于判断是否相撞的形状叫**碰撞几何**。碰撞形状通常更简单，以减少计算量，但关键接触面不能失真。两套形状要分别保存版本，并检查尺寸和相对位置。形状过粗会改变可抓位置；过细或不规范的网格也可能让接触计算不稳定。

<span id="3-机器人本体与执行器"></span>

### 身体怎样运动，还取决于重量和驱动方式

同一个杯子，空着和装满水时，提起与停下的反应不同。模型中的**惯性参数**描述这类差别：物体多重、重量集中在哪里，以及绕不同方向转动有多困难。只给模型画好外壳，还不足以算出这些反应。

机械臂也需要正确的关节方向和活动范围。假如模型把一个关节的正方向写反，数据中“向托盘移动”的命令，回放时就可能让夹爪远离托盘。因此要先做简单动作，确认模型的身体和预期一致。

收到“把杯子移到托盘上方”的命令后，手臂还需要时间加速和停下。**执行器模型**描述命令怎样驱动关节，以及响应速度和输出限制。仿真手臂若总能立刻、准确地到位，真实电机却有延迟或速度限制，训练样本就会过于容易。

<span id="控制接口必须和数据语义一致"></span>

### 相同的数字，可能是完全不同的动作

例如动作里写着 `0.2`，它可能表示转到某个角度，也可能表示某个转速或力矩。这个数字仅用于说明歧义，没有实测含义。记录前必须约定动作的意思和单位，否则别人拿到这条数据，也不知道怎样让机械臂做出同一个动作。

还要记下“想让手臂怎样动”和“最后实际给了什么命令”。两者可能经过转换，例如先根据夹爪的目标位置算出各关节该转多少。具体控制方式和对应字段见附录。

<span id="4-接触材质与求解设置"></span>

### 接触参数会改变成功与失败

杯子能否被提起，同时取决于碰撞形状、摩擦、接触有多“软”、计算的时间步长，以及求解器设置。求解器就是每一步计算这些相互作用的程序。MuJoCo 与 Isaac Sim/PhysX 的参数含义并不总是一一对应，跨引擎比较时应对照滑移、接触力和运动轨迹等结果。

先观察简单现象：桌上的物体是否自行滑动或抖动，夹爪是否穿入物体，关节是否越限，改变步长后任务结果是否突然翻转。这些检查比只看一次完整任务动画更容易发现问题。

## Who｜谁负责准备与确认这些配置？

搭场景的人、让机械臂运动的人和使用数据的人需要一起确认它能用；小项目里也可以是同一个人。重点是让每个配置都能说清依据。

以杯子滑落为例，建模者先核对杯子重量与表面设置，控制者检查夹爪实际夹了多紧，数据使用者再核对记录能否解释这次失败。如果只看最终的“失败”标签，就很难知道应该改哪一步。

正式采集前，负责质量检查的人把这些结果与真实测量或事先约定的范围对照，确认当前场景适合预定用途。

## Where｜配置保存在哪里，又随数据交给谁？

配置保存在场景文件及其引用的模型、图片等文件中；采出的数据要能找回当时使用的那一套配置。例如同一个杯子后来改重了，旧数据仍应指向原来的版本。

只保存一个入口文件还不够，它引用的杯子模型或材质也可能变化。从其他格式导入时，还可能丢失重量或关节设置，所以导入后要重新看一遍杯子的接触和机械臂的动作。

这些文件与配置通过**场景清单**联系起来，可以把它看作这套练习场的装配说明。它跟随数据交给下一位使用者，让对方知道杯子为什么这样运动，也能重新搭出相同条件。若每轮改变杯子的位置或重量，还要保存那一轮实际采用的值。

这份清单随后用于解释[传感器记录](/simulation/simulation-sensors-timing/)，并与[每次任务的数据](/simulation/simulation-task-generation/)绑定。模型格式与清单字段见附录；具体实现见[MuJoCo 与具身数据](/simulation/mujoco-embodied-data/)和[Isaac Lab 与具身数据](/simulation/isaac-lab-embodied-data/)。

<span id="5-建模校验与冻结"></span>

## When｜什么时候可以开始正式生成数据？

当简单动作表现合理，完整的放杯子任务也能正确区分成功与失败时，就可以开始采集。先把杯子放在桌上看它能否静止，再试夹爪闭合、提起、移动和松手，逐步检查比直接看一段完整动画更容易找到原因。

![场景依次经过几何坐标、运动学、动力学与真实设备对照四层校验](/images/docs/simulation-physics-validation.svg)

检查时先确认“摆得对不对”，再看“动得对不对”。例如托盘位置正确后，才值得比较手臂是否停得准；杯子能正常落在托盘上后，再与真实设备对照接触和放稳的过程。

通过后，固定这一版模型、资产依赖、控制参数、物理设置和检查结果，让同一批数据引用它。引擎或模型升级时重跑这些用例，才能判断新旧数据是否仍可一起使用。

“可复现”也要说明范围。先检查同一机器重复运行时，误差是否落在约定范围内。换硬件或引擎版本后，需要重新检查；不能因为配置文件相同，就假定每个数值都会一致。

## 技术附录：动作接口与交付字段

<details>
<summary>实施记录器时，展开查看需要保存的字段</summary>

关节记录应写明名称、顺序、类型、单位，以及各关节占据的数组范围。数组长度不能直接当作关节数量：自由关节的朝向通常用四元数表示，即用四个数共同表达一个朝向。

惯性参数包括质量、质心和惯性张量，后者描述质量围绕不同转轴的分布。执行器还应记录响应强度（增益）、输出达到上限的情况（饱和）、延迟，以及适用的死区和速度限制。

位置控制常用 **PD 控制**，根据位置误差和速度误差计算控制量。末端位姿控制可能先做**逆运动学**，由夹爪的目标位置与朝向求出关节配置。两者都要保存实现版本和关键参数。

不同动作接口需要不同的补充信息：

| 动作含义 | 必须连同动作保存的信息 |
| --- | --- |
| 关节位置目标 | 控制器增益、限速与限位、实际关节位置 |
| 关节速度目标 | 控制周期、加速度或力矩限制、饱和状态 |
| 关节力矩 | 请求与施加力矩、裁剪规则、执行器延迟 |
| 末端位姿目标 | 目标坐标系、逆运动学版本、生成的关节命令 |

若训练用末端增量、真机用关节位置，中间转换器也属于数据来源与验证范围。物理、控制和采样周期的关系见[仿真传感器、渲染与时间对齐](/simulation/simulation-sensors-timing/)。

</details>

<span id="交付给下游的数据契约"></span>

<details>
<summary>场景清单示例</summary>

常见模型入口中，**URDF** 主要描述机器人连杆、关节、惯量和几何；**MJCF** 是 MuJoCo 的模型格式，还可描述场景、执行器、传感器与求解选项；**USD** 用于组织 Isaac Sim 的场景、资产引用和变体。

每个资产应有稳定的 ID 和来源记录。格式转换后，重新检查坐标轴、关节方向与限位、惯量、碰撞形状、执行器和传感器，并固定外部依赖及导入配置。

```text
scene_manifest
  engine_name / engine_version / solver_config
  robot_id / model_file_hash / dependency_hashes
  visual_geometry / collision_geometry
  units / world_frame / joint_layout
  mass_inertia / actuator_config / joint_limits
  contact_materials / gravity / physics_timestep
  task_objects / initial_state_distribution
  conversion_tool_version / import_options
  validation_suite_version / validation_results
```

`solver_config` 应包括求解器和积分器设置；积分器负责根据当前状态和受力推进下一时刻。模型哈希用于核对文件内容是否相同，不能只用文件名代替版本。

固定检查用例可包括自由下落、桌面静止接触、单关节响应、夹爪闭合、典型成功与故意失败任务，每项保存初态、动作序列和预期结果范围。换 GPU、引擎版本，或从 MuJoCo 切换到 MJX 时，分别报告数值误差与任务结果，不默认逐位一致。

</details>
