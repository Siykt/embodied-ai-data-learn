多机器人协作数据记录一组机器人怎样共同完成任务。它既包含每台机器人的观测和动作，也包含任务分配、相互通信、物体交接、共享地图以及共同结果。两台机械臂抬同一口锅时，单独看任意一台的轨迹都可能合理；如果一台开始抬升时另一台尚未握稳，团队仍会失败。因此，团队记录不能只是几份单机器人日志的集合。

可以把一次共同尝试定义为**团队 episode**：它有共同任务、参与成员、开始与结束条件，成员轨迹通过消息和交接事件关联。每个成员保留自己的时钟、观测范围与执行状态，团队层再记录谁在何时根据什么信息做出决定。以下字段是本站的数据工程建议，不是各论文共同发布的标准格式。

## 一、协作过程需要保存哪些证据

### 语义消息与实际行动

**语义通信**是用可解释的任务信息交流当前意图、状态或请求，例如“我已握住左侧把手，请准备抬升”。[DuoMind](https://arxiv.org/abs/2610.02161)让各机器人的高层协调器读取本地观测及对方消息，再给动作模型下达子任务指令。数据启示是把原始任务、协调消息、下达指令和实际动作串起来；一条“已经抓稳”的消息仍需接触或执行证据支持，不能直接当成物体状态真值。

**物理耦合**指一个成员的动作会通过共享物体或接触关系改变其他成员的受力和运动。[Watch, Infer, Coordinate](https://arxiv.org/abs/2610.02170)研究从双方联合行为推断伙伴的物理能力限制。另一台机器人可能补偿其伙伴的弱点，因此应同时保留双方动作、共享物体运动和已知故障条件；只用受限机器人的成功动作，无法证明它独立具备同样能力。

### 人员协作与角色轮换

[协作遥操作界面研究](https://arxiv.org/abs/2610.15001)比较同地共享界面、远程共享界面及同地独立界面，记录任务表现、行为和操作者负荷。采集时应把操作者身份、所控制机器人、可见界面、沟通条件和交接时刻放入同一任务记录。**角色交接**是某项职责从一个成员转给另一个成员的过程；“发出交接请求”“对方确认”“新成员真正执行”应是不同事件。

[PingpongDuo](https://arxiv.org/abs/2610.20579)把双打中的严格交替击球、让位和队友碰撞风险纳入协调，并使用人类双打步法参考及真实球飞行、接触测量校准仿真。它提示数据应区分当前击球者、等待者、让位阶段和角色切换，同时保存人体参考、仿真标定与机器人执行的来源关系。比赛规则满足与动作精度需要分别打分。

### 共享地图与成员参与

[协同具身搜索研究](https://arxiv.org/abs/2610.15038)将模型提出的区域、目标位置与连接视作不确定假设，再利用观测修订。**共享状态**是团队当前共同使用的地图、对象或任务状态版本；它可能包含推测。每个假设要记录提出者、证据、置信度、验证状态及被撤回的原因，避免后处理把最终地图回填成机器人当时已经知道的信息。

[MPT](https://arxiv.org/abs/2610.22322)通过成员竞价决定谁参与行动，并把集体结果转成局部训练反馈。**参与竞价**在此指成员表达参与某项行动意愿的数值，并非货币交易。对其机器人导航部分，数据应保存所有候选成员的竞价、选择结果、实际执行者与局部反馈；仅记录胜出者会隐藏未被选中的能力与分工变化。论文同时含通用研究任务，那部分结果不能外推为机器人协作能力。

## 二、采集、时间对齐与空间关系

1. **建立团队清单。** 在采集前固定任务成功条件、成员及操作者、角色约束、通信条件和共享物体；成员中途加入或退出时记录事件，不改写初始清单。
2. **保留各自原始流。** 分别采集相机、机器人状态、控制命令、接触和安全事件；不要为了形成一张整齐的表而覆盖原始采样时间。
3. **记录消息因果。** 消息至少包含发送、接收和首次用于决策的时间及关联 ID。发送时间相同不表示接收同时，接收成功也不表示动作已经生效。
4. **建立统一参考。** 保存本地时钟到团队时间的映射、同步误差、各机器人基座到共同世界坐标的变换，以及物体和接触点坐标系。机器人移动后，变换需要相应的时间版本。
5. **关联共同事件。** 把交接、共同抬升、成员退出、目标发现或碰撞连接到各成员相关时间段，保留等待、误解和失败恢复片段。

一个重要检查是：决策时所用的消息是否已经到达。如果某台机器人在动作开始后才收到伙伴状态，训练标签就不能把这条消息当作动作输入。共享地图也应按“当时可用版本”回放，而不是使用任务结束时最完整的地图。

## 三、最小数据字段

| 字段组 | 建议字段 | 用途 |
| --- | --- | --- |
| 团队任务 | `team_episode_id、task_spec、team_members、joint_success_rule` | 定义共同尝试和团队成功条件 |
| 成员与角色 | `agent_id、operator_id、embodiment_version、role_interval` | 区分硬件、控制来源和角色变化 |
| 局部轨迹 | `observation_id、command、applied_action、t_sample、t_apply` | 重建成员当时所见与实际执行 |
| 通信 | `message_id、sender、receiver、t_send、t_receive、used_by_decision` | 检查消息延迟、丢失及决策因果 |
| 共享状态 | `state_version、entity_id、claim、evidence_ids、verification_state` | 区分观测、推断、撤回与已验证状态 |
| 联合事件 | `event_id、participants、handover_phase、contact_state、object_pose` | 解释交接与物理耦合 |
| 选择与结果 | `candidate_bids、selected_agent、local_feedback、team_outcome` | 还原分工、贡献及团队结果 |
| 来源与划分 | `source_session、policy_versions、calibration_versions、split` | 保持可追溯与评估隔离 |

字段可按场景裁剪：没有竞价机制时不造一个竞价值；通信故意关闭时应记录该实验条件。对于未知状态，使用明确的缺失或未验证标签，不能填零后让下游误认为有效测量。

## 四、质量控制与团队评估

![协作评估分别核查时间与坐标证据、团队成功和碰撞交接指标，再通过关闭通信及更换伙伴等对照分析协作收益](/images/docs/multi-robot-coordination-data-evaluation.svg)

首先检查证据质量：成员流是否完整，消息是否能找到收发两端记录，时钟误差是否足以分辨交接顺序，共享物体在各相机或机器人坐标中的位置是否一致。出现成员掉线时，团队成功标签不能掩盖缺失轨迹；可以保留该 episode，但要说明适合故障分析还是完整监督训练。

其次分别报告团队与成员指标。团队层看共同任务成功、完成时间、碰撞、重复搜索和遗漏目标；成员层看等待时间、工作量、交接延迟、执行失败与接管。工作量均衡不一定最优：能力不同的机器人可能应承担不同任务，需结合任务分工和能力约束解释。

最后设计可比对照。关闭通信、更换伙伴、引入消息延迟或成员退出时，尽量固定任务、随机种子、感知与执行模型和总预算，记录改变的因素。训练与测试至少按团队 episode 和源场景隔离；同一次交接的双方轨迹必须进入同一 split。若宣称伙伴泛化，还应留出未见伙伴或未见能力约束组合。

## 五、研究结论的使用边界

DuoMind 的证据来自 RoboPoly 与 RoboTwin 仿真；其消息消融说明信息共享对这些任务有帮助，不能直接证明真实网络下的可靠性。协作遥操作研究为 16 人、8 对非专家参与者与两台模拟机器人，三种条件并非完整的两因素四组合实验；其中部分抓取操作被简化，结果应限定为该界面与任务协议。

协同搜索研究的 100 个测试用例来自 5 个 Matterport3D 扫描。全文说明，当次实验生成的假设边未通过准入检查而被移除，因此没有报告边存在或距离的准确率；不能据此宣称模型已可靠修正幻觉拓扑。PingpongDuo 有真机双机器人结果，但其速度、交替规则和标定条件不能替代其他合作任务的验收。能力推断与竞价协作也必须根据具体任务和数据证据判断，不能把团队成功自动归因于每个成员能力提高。
